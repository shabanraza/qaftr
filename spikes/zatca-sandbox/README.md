# ZATCA developer-portal sandbox spike

A throwaway proof of concept that runs the whole Phase 2 flow against ZATCA's **public developer-portal sandbox**
(`https://gw-fatoora.zatca.gov.sa/e-invoicing/developer-portal`). It uses keys generated on the spot plus ZATCA's
documented sandbox values (OTP `123345`, VAT `399999999900003`). No real taxpayer data, no portal account.

The signing path is plain TypeScript with `@noble/curves` (secp256k1) and `@noble/hashes`. It uses no OpenSSL and no XML library, so
the same code can run in a Cloudflare Worker or in a browser.

## Run

```bash
cd spikes/zatca-sandbox
npm install                      # @noble/curves + @noble/hashes only
node --experimental-strip-types src/run.ts        # Node >= 22.6 (or: bun src/run.ts)
node --experimental-strip-types src/negative-tests.ts
java verify/HashCheck.java out/report-simplified.xml   # independent C14N 1.1 hash check (JDK 17+)
```

Output goes to `out/`, which is gitignored: the throwaway private key, CSR, signed XMLs and `responses.json` with tokens redacted.

## What it does

| Step | File | Result on 2026-11-09 |
|---|---|---|
| 1. secp256k1 key + CSR (pure TS DER encoder) | `src/csr.ts`, `src/der.ts` | `openssl req -verify` OK |
| 2. `POST /compliance` (OTP 123345) → CCSID | `src/api.ts` | 200 ISSUED, cert issued **for our key** |
| 3. `POST /compliance/invoices` × 6 (simplified + standard × invoice/credit/debit), ICV/PIH chained | `src/invoice.ts`, `src/qr.ts` | all 200 PASS, no warnings |
| 4. `POST /production/csids` → PCSID | | 200 ISSUED (a fixed sandbox cert, **not** bound to our key) |
| 5. `POST /invoices/reporting/single` (simplified) | | 200 REPORTED |
| 6. `POST /invoices/clearance/single` (standard) | | 200 CLEARED, stamped XML returned |

## Findings

* The first reporting attempt failed with `signed-properties-hashing` ("Invalid signed properties hashing").
  ZATCA hashes `xades:SignedProperties` with namespaces declared where they are used (`xmlns:xades` on SignedProperties,
  `xmlns:ds` on every `ds:*` child) and with **self-closing** `<ds:DigestMethod .../>`. That is not strict C14N. Once the
  serialization matched, the call was accepted. The compliance-check endpoint did **not** catch this error. Only reporting did.
* **The developer-portal sandbox is lenient.** `src/negative-tests.ts` shows that:
  * a wrong `invoiceHash` in the request body is rejected (`invoiceHash_QRCODE_INVALID`)
  * a broken QR is rejected (`QRCODE_INVALID`)
  * an XML **changed after signing** is still REPORTED
  * an XML **signed with an unrelated key** is still REPORTED

  A sandbox PASS therefore does not prove that the hash or signature is correct.
* The invoice hash was checked independently with the JDK's built-in C14N 1.1 (`verify/HashCheck.java`). The hashes MATCH.
  Reordering attributes or changing quotes in a copy still matches. Editing the content gives a mismatch.
* The signature is ECDSA-SHA256 over the 32-byte invoice digest. This is the scheme used by the widely deployed OSS
  implementations. **Still to do:** check it with the official SDK (`fatoora -validate`), which checks
  the signature against the certificate. Run it with the CCSID certificate, since the sandbox PCSID is not bound to our key.

## Caveats and next steps

* Single 15% VAT category only. No discounts, exemptions (Z/E/O + reason codes), multi-currency, prepayments or
  `cac:Delivery` rules for simplified documents.
* The renewal call (`PATCH /production/csids`) is not exercised.
* Next environment is **simulation** (`/e-invoicing/simulation`). It needs an OTP generated by a real taxpayer in the
  Fatoora *simulation* portal, and template name `PREZATCA-Code-Signing`. The spike stops at the developer portal on purpose.
